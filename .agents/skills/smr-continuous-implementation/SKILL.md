# Continuous implementation

Read the [continuation contract](../../../CONTRIBUTING.md#continuous-implementation)
when establishing the workflow. Use existing issues and Orca Tasks as the queue;
private `.handoff/START_HERE.md`, when present, routes current operational authority.
Loading this skill does not resume paused work or grant new authority.

Choose the next observable outcome and its discriminating check. Deliver a useful
slice through integration and acceptance; a review, commit or handoff is an
intermediate result when required work remains.

Before implementing missing tooling, check the installed capability and the path
from source through verification and deployment to the intended outcome. Surface
host restarts, unavailable toolchains and human permission requirements before
coding; inspect build hooks for side effects. Do not equate a reviewed patch with
an operational capability.

Apply the contract's [short investigation bounds](../../../CONTRIBUTING.md#keep-investigations-and-preparation-short):
normally 10 minutes for a small capability assessment and 30 minutes for its narrow
source slice, including checks/review. Keep the original elapsed interval across
renamed subtasks. Escalate an exact material blocker immediately; after 15 minutes
without an outcome or decision-changing fact, change the approach. These are
planning defaults, not mechanical enforcement or replacements for runtime limits.

Before recommending or handing off a runtime pilot, inspect the concrete path to
its complete outcome. An interface, passing synthetic tests or available hooks do
not establish an implemented operator. Identify missing save/reopen/cleanup steps
before asking the user to prepare. Human assistance is an option only when its
actual interaction and preservation path are supported; it cannot turn historical
screenshots into current input authority.

Before retrying a failure, identify the failed expectation, proposed cause, changed
input or hypothesis, and observation that would distinguish the cause. A different
explanation alone is insufficient: the next action must test it. Repeating an
unchanged attempt without new evidence is a loop, not recovery.

Keep a compact failure/cause/attempt/result/next-decision note in the existing Task
or handoff. Recognize the same failure across renamed tasks, workers and sessions.
Reuse accepted checks when their relevant inputs and environment remain unchanged.
Do not reopen settled reviews without a concrete changed risk.

When an approach repeats, stop that approach, retain its evidence, and select a
discriminating diagnostic or independent ready work. Use independent help only for
a specific unresolved question or required review; no recursive review chain.
Also recognize a broader loop: repeated helper changes, fixtures and reviews can
all differ while the same end-to-end outcome remains unreachable. After a failed
attempt, identify what acceptance advanced or uncertainty was resolved and whether
the next task reaches the missing outcome. If only supporting machinery expands,
stop that approach and reassess the shortest complete path. A narrow diagnostic or
pilot does not authorize unrelated work or an implementation chain.

Do not turn an agent-imposed one-trial restriction into a permanent project ban.
A separately scoped repair with a changed, supported hypothesis may be ready work;
it cannot reuse a consumed grant. Give the coordinator a concrete next decision,
not repeated “blocked” summaries. Do not require routine user confirmation within
existing authority or invent work merely to keep the Goal active.

A diagnostic whose intended positive control fails is inconclusive. Do not use
its empty result as evidence that the target scene or behavior is absent. Preserve
the failed control and seek independent evidence before tuning the query. Record
human observations as such, including whether they concern a retained artifact or
a current live state; neither automatically validates the failed detector.

Continue independent work while signing or another lane waits. Ask the user only
for a material decision, missing authority/authentication, or genuine blockage.

At natural checkpoints, record the accepted outcome or newly resolved uncertainty,
its evidence, remaining work and next action. Apply the contract's evaluation
record; do not build a second tracker. Preserve honest source/runtime/save evidence
and all existing safety controls. Instructions are not a mechanical loop detector.

When designing or scoring skill validation, use the evaluator-only
[evaluation cases](references/evaluation.md). An agent being tested receives only
the request and task artifacts, not that reference's expected decisions.
Do not load the reference for routine work.
